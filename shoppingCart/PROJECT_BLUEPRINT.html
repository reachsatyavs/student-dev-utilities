01

Problem statement

Most beginner web tutorials stop at "hello world," and most real e-commerce codebases are too large to read end to end in a course. Students need something in between: a project small enough to hold in your head in a few sessions, but with all the moving parts a real online store actually has — an account system, a product catalog, a cart that remembers what you added, a checkout that turns a cart into a permanent order, and an admin who can manage users and stock.

Without that middle step, students either copy a tutorial they don't fully understand, or feel lost the first time they see a real production codebase.

02

Goal

Build a working shopping cart web app — and, just as importantly, learn the habit of thinking in this order:

Feature → User Story → Use Case → Test Case

Every button a shopper clicks should trace back to a reason a real person wanted it (a feature, told from their side as a user story), a precise description of how the system behaves when they use it (a use case), and a concrete way to prove it still works (a test case). Sections 6–10 below walk that whole chain, fully linked.

03

Overview

The app is a small but complete online store. A shopper registers, logs in, browses a product catalog (with search and category filters), adds items to a cart, and checks out — which turns the cart into a permanent order. An admin has a separate area to manage user accounts and the product catalog, including pulling in sample products from a public API instead of typing them by hand.

It's deliberately small: no payment gateway, no shipping logic, no microservices — one Flask app, one SQLite file, plain HTML templates. That's what makes it possible to trace every feature all the way down to a test case, instead of just the interesting ones.

04

Tech stack

Deliberately short — five real dependencies, one of them already inside Python.

Python 3.10+

The language everything else runs on.

Flask 3

Routes requests to Python functions and renders HTML.

Flask-SQLAlchemy

The ORM — Python classes in models.py instead of raw SQL.

Flask-Login

Session handling — who's logged in, on every request.

SQLite

The entire database is one file. Ships inside Python — nothing to install.

Jinja2 + Bootstrap 5

Server-rendered templates, styled via CDN — no frontend build step.

python-dotenv

Loads settings from .env — no secrets hardcoded.

requests

Calls dummyjson.com to sync sample products.

Use cases

How the system actually behaves, step by step, for each group of stories. Click a row to expand it.

UC1 Register account▶
Actor: Guest (not logged in)Precondition: visitor is on the Register page
Main flow
  1. Visitor enters username, email, password and confirm-password.
  2. System checks: all fields filled, password ≥ 8 characters, password matches confirm, username not already taken, email not already taken.
  3. System hashes the password and creates the user record.
  4. System redirects to Login with a success message.
Alternate flow

Any failed check re-shows the Register form with a specific error message; no account is created.

UC4 Browse & search products▶
Actor: Logged-in shopper
Main flow
  1. Dashboard loads every product, sorted by title.
  2. Shopper types a keyword; the system filters titles (case-insensitive, partial match).
  3. Shopper picks a category; the system narrows the list to that category.
  4. The filtered grid re-renders — search and category can combine.

UC5 Manage cart▶
Actor: Logged-in shopper
Main flow
  1. Shopper clicks "Add to cart" on a product with a chosen quantity.
  2. If that product is already in the cart, its quantity increases instead of creating a duplicate row (a database constraint enforces one row per user/product).
  3. On the Cart page, shopper edits a line's quantity — setting it to 0 deletes the line.
  4. Shopper removes a line directly with "Remove."
Alternate flow

Trying to update or remove a cart line that belongs to a different user is blocked with "You cannot modify another user's cart."

UC6 Checkout▶
Actor: Logged-in shopperPrecondition: cart has at least one item
Main flow
  1. Shopper clicks Checkout.
  2. System totals the cart, creates an Order (status "placed"), and copies each cart line into an OrderItem — locking in today's price.
  3. System deletes the checked-out cart lines.
  4. System redirects to an Order Confirmation page.
Alternate flow

Checking out an empty cart shows a warning and creates nothing. Opening someone else's order-confirmation link is blocked and redirected to the Dashboard.

UC7 Manage users (admin)▶
Actor: AdminPrecondition: logged in with is_admin = true
Main flow
  1. Admin opens Admin → Users and sees every registered user, newest first.
  2. Admin enters a new password (≥ 8 characters) for a chosen user.
  3. System hashes and saves it; that user can log in with it immediately.
Alternate flow

Any non-admin who requests an /admin/... URL gets a 403 Forbidden page instead of the content.

UC8 Manage products (admin)▶
Actor: Admin
Main flow
  1. Admin opens Admin → Products and sees the full catalog.
  2. Admin adds a product by entering a title, price, stock, category, description and thumbnail URL.
  3. Admin deletes a product that has never appeared in a placed order.
  4. Admin syncs the catalog from dummyjson.com to bulk-add sample products.
Alternate flow

Deleting a product that already appears in someone's order history is blocked, so past orders always stay intact.
